# cx 自然使用频度：首轮描述 A/B 实验

日期：2026-09-17。结论：**候选描述增加了 GPT‑6 的调用频度和首选率，但未提高整体任务采纳率；本轮不将更长的候选描述替换为生产默认值。**

这里的“未采用”是实验结果，不是实现完成了普遍优化。候选、基线、用例、采集器及统计脚本均保留，可继续比较后续方案。

## 方法与完整性

详见 [README.md](README.md)；机器可读逐样本结果见 [results/2026-09-17.json](results/2026-09-17.json)。

- 开源库 `tkem/cachetools`，固定 `v5.5.2` / `c403f9f4185e58090b904c1915345b9ba46d5a08`。
- 三个模型并行，三个真实编辑任务，每个任务分别运行原描述与候选描述；共 18 次独立会话、18 个仓库副本。
- 任务提示不提 cx、不指定导航工具。只有工具 `description` 改变；保留原有 schema、工具实现、promptSnippet、promptGuidelines。
- 候选在测试前冻结，采用“使用场景 → 返回内容 → 最小参数 → 能力边界”的写法；不是强制调用策略。
- 实际暴露审计：18/18 使用指定模型、medium reasoning，19 个活跃工具顺序一致；全部 cx 描述和参数符合各自条件。剔除 cwd 和输出路径后，18 个系统提示完全一致。
- SDK 运行时 Pi 0.85.1；项目开发依赖 0.85.0；pi-subagents 0.68.0；cx 源码基线 `9a497c8b7ee952ab1e0e7827fb55ecd569c0d7c9`，测试使用捆绑原生资源。
- 所有索引由宿主预热；预热不作为模型调用计数。

## 配对主结果

`r12`（DeepSeek / invalidate / 原描述）在过程中发生 `Stream ended without finish_reason`。原生运行最终完成，但为避免把异常恢复过程当作正常选择行为，主分析剔除该样本及其配对候选 `r09`。因此比较 **8 对完整样本**，而不是不对称地比较 8 与 9 次。

| 模型 | 完整任务对 | 至少使用一次 cx：原 → 候选 | cx 调用数：原 → 候选 | 导航调用中 cx 占比：原 → 候选 |
|---|---:|---:|---:|---:|
| GPT‑6 (`amazon-bedrock/global.openai.gpt-6-astra`) | 3 | 3/3 → 3/3 | 9 → 17 | 9/26 = 34.6% → 17/28 = 60.7% |
| Kimi K3 (`aliyun/kimi-k3`) | 3 | 1/3 → 1/3 | 1 → 1 | 1/30 = 3.3% → 1/29 = 3.4% |
| DeepSeek (`aliyun/deepseek-v4.1-flash`) | 2 | 0/2 → 0/2 | 0 → 0 | 0/27 → 0/30 |
| **合计** | **8** | **4/8 → 4/8** | **10 → 18** | **10/83 = 12.0% → 18/87 = 20.7%** |

“导航调用”包括 read/grep/find/ls/cx，和含常见检索/读取命令的 bash 调用；bash 分类是启发式。更客观的全工具调用占比为 **10/124 = 8.1% → 18/133 = 13.5%**。

其他观察：

- GPT‑6 首个导航工具从 **0/3 使用 cx → 3/3 使用 cx**，这是本轮最清楚的积极信号。
- 增加的调用是 overview/definition/changes 等正常查询，**没有 cx 工具错误、没有空结果、没有重复 refresh 刷计数**。
- Kimi 两组各只调用一次 `cx_overview`，其他导航主要仍用基础工具；DeepSeek 所有六次运行都未调用 cx（包括被排除的两个样本的观察记录）。
- context/callers/callees/references/impact/map 未获得使用证据。这些任务未充分覆盖调用关系、跨模块影响与陌生大型项目探索，不能据此判断这些工具本身无用。
- 两次 bash 非零退出来自 GPT 主动运行红测试，是有效回归验证，不是 cx 错误或最终任务失败。

## 完成质量与成本

宿主对 **18/18** 最终代码重新执行了：

1. 原始上游冻结测试（216 项）；
2. 各样本仓库内包含新增回归测试的完整 pytest；
3. 外部行为验收（修订版 v2，见下方）。

全部通过。`r12` 的代码验收通过与它的运行轨迹被排除并不冲突，代码质量和运行完整性分开记录。

| 模型 | 配对样本平均耗时：原 → 候选 | 累计报告 tokens：原 → 候选 |
|---|---:|---:|
| GPT‑6（各 3 次） | 47.7s → 53.0s | 346,328 → 514,043 |
| Kimi（各 3 次） | 166.2s → 175.0s | 414,758 → 501,855 |
| DeepSeek（各 2 次） | 137.8s → 101.7s | 788,645 → 493,695 |

Tokens 是模型报告的 input + output + cacheRead + cacheWrite 累计量，包含多轮重复上下文，**不是独立上下文大小或直接计费金额**。不同 provider 的报告口径和缓存行为不保证等价。

GPT‑6 的 cx 调用增加约 89%，但同时观察到总工具调用 49 → 55、耗时约 +11%、累计报告 tokens 约 +48%。候选描述总字符数从 **1,580 → 4,040**，约 2.56 倍。样本很小，不能把成本差异全部归因于描述；但也没有证据支持它是一项效率优化。

### 验收断言错误

最初 `acceptance.py` 在 invalidation 后比较整个 `cache_info()` 元组不变，错误地包含了应该减少的 currsize。该断言与用户任务要求的“hits/misses 不变”冲突。

- 保留 v1 验收文件、原始失败日志和首次统计。
- v2 只修正为 hits/misses/maxsize 不变、currsize 减少到预期值。
- 修正后的测试对未修改上游仍因缺少新能力失败，对所有模型产物统一重验通过。
- 测试修订发生在运行结束后，不影响任何模型的工具选择；不能称验收脚本从头到尾完全未改。

### 类型与测试环境

观察器有一次仅类型层面的 `as unknown as ExtensionAPI` 修正，不改变执行行为。项目完整扩展测试最初因未构建 `target/debug/cx` 失败；随后使用测试支持的 `PI_CX_TEST_BINARY` / `PI_CX_TEST_GRAMMARS` 指向捆绑资源，42/42 通过。

最后一次检查时 `/usr/bin/git` 因当前 Xcode 许可状态拒绝启动。使用已安装的 `/Library/Developer/CommandLineTools/usr/bin/git` 后，Git 差异检查和全部宿主验收重跑通过；没有修改许可、系统选择或用户配置。统计器也会在 Git 取证失败时明确报错，不把空 stdout 保存成“无差异”证据。

## 决策

**不直接发布这套更长的候选描述。** 理由：

1. 总体“会不会用”的采纳率没有提高，只增加了原本会用的 GPT‑6 的频度。
2. Kimi / DeepSeek 的主要问题没有得到解决；不能用 GPT 的结果代表三个模型。
3. 描述显著变长，而 GPT/Kimi 的耗时和累计 tokens 没有改善。
4. 单一小库、每格一次运行、无 held-out 项目，不能宣称统计显著或多项目普适收益。

因此 `extensions/pi-cx/tools.ts` 保持不变。`candidate.json` 是保留的实验候选，不是已生效配置。

另外确认了一个独立的配置因素：Pi 内置 worker/delegate 使用严格工具白名单，并不自动获得父会话的 cx。这是某些**子代理**场景中“不可能使用”的原因；本轮通过显式配置消除了它，但没有证据证明它解释用户主会话中的低使用率。本次未修改用户全局配置。

建议下一轮把干预拆开，而非继续堆长 description：

- 独立测试更短的场景描述与更明确的 promptSnippet/promptGuidelines（任务提示仍不提 cx）。
- 增加两个 held-out 仓库和跨语言任务，覆盖不知道文件位置、追踪调用者、跨文件修改；加入只改文档/配置的负对照。
- 每格多次重复；分别比较采纳率、首次选择、有效检索次数、代码通过率与成本。不能为了增加使用率而惩罚合理的 read/grep。
